Control Decision Diagnostics Implementation Plan

Goal

Add a read-only control diagnostics view so the dashboard can answer whether live data acquisition is healthy, which battery should charge/discharge/hold/skip, and why a charge/discharge write is not being attempted.

Non-Goals

  • Do not add new EcoFlow write commands.
  • Do not loosen existing real-control gates, command intervals, retry suppression, or safety thresholds.
  • Do not expose API tokens, private MQTT credentials, device serial numbers beyond the existing device status surface, or confirmation strings.
  • Do not redesign the whole dashboard layout.

Current State

GET /api/status returns grid import/export, DELTA Pro 3 status, surplus plan, night charge plan, DELTA 3 auxiliary plan, tariff context, and control write readiness. GET /api/devices/statuses returns configured charging-device telemetry where supported. The dashboard polls status every 10 seconds and device statuses every 30 seconds, but users still infer the current control reason manually.

Data/API Contract

Extend domain.Status and /api/status with an optional controlDiagnostics object containing grid state, data freshness, write readiness, DELTA Pro 3 diagnostics, auxiliary battery diagnostics, and a short summary. The diagnostics are derived from existing status values only, do not call external APIs, and do not persist new data.

Frontend Contract

Add a compact 制御診断 section near the top of the dashboard with grid state, data freshness, write readiness, DELTA Pro 3 action/reason, auxiliary action/reason, and warnings for stale/error/blocked conditions.

Safety Boundaries

  • Read-only only: no write APIs, no new command send paths, no real-device state changes.
  • Keep existing ControlWriteReadiness as the source of gate state.
  • Do not include secret-bearing config values in the diagnostics payload.
  • Treat missing telemetry as unavailable and show it as a blocker instead of guessing.
  • If grid/Nature data is stale or errored, diagnostics must say the control basis is uncertain.

Implementation Steps

  1. Add ControlDiagnostics domain structs.
  2. Build diagnostics in status_handler.go after readiness is calculated.
  3. Add backend tests for importing, exporting, stale/error, and sanitized blocker behavior.
  4. Extend frontend TypeScript types.
  5. Add display-label helpers for diagnostic actions/grid states.
  6. Add a compact dashboard diagnostics card.
  7. Add minimal CSS for compact rows.

Review Points

Diagnostics must not leak secrets, imply writes were sent, hide stale/error state, or increase the device status row height. Missing telemetry should remain readable.

Verification Commands

  • cd backend && rtk go test ./internal/api -run TestStatusHandler
  • cd backend && rtk go test ./...
  • cd frontend && rtk npm run build
  • git diff --check
  • When practical: docker compose up -d --build, curl -s http://localhost:${HTTP_PORT:-8080}/api/status or the local .env port such as 18085, and browser confirmation.

Rollback / Operational Notes

The change is read-only and additive. If diagnostics are misleading in operation, hide the card first rather than changing real-control thresholds.
